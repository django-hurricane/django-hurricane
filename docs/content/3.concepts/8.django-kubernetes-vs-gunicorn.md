# Django on Kubernetes: Hurricane vs. Gunicorn & uWSGI

When deploying Django into a modern Kubernetes cluster, selecting the right application server dictates cluster stability, memory utilization, and zero-downtime rolling update performance.

Traditional Python application servers like **Gunicorn** and **uWSGI** were designed over a decade ago for long-lived, multi-tenant virtual machines. While battle-tested on static servers, their multi-process master/worker architecture creates severe architectural friction when containerized inside ephemeral Kubernetes Pods.

**Django Hurricane** was designed from the ground up as a **Kubernetes-native application server**, replacing legacy Python event loops and process forkers with a high-performance **Rust Hyper/Tokio core** (powered by **[Granian](https://github.com/emmett-framework/granian)**) and native Kubernetes lifecycle integrations.

---

## Architectural Comparison Matrix

| Feature | Gunicorn + Uvicorn Worker | uWSGI | Django Hurricane (v2.0) |
|---|---|---|---|
| **Underlying HTTP Engine** | Python socket loop (`asyncio`/`sync`) | C core with custom protocol | **Rust Hyper & Tokio ([Granian](https://github.com/emmett-framework/granian))** 🦀 |
| **Container Concurrency Model** | Multi-process fork model (heavy RAM tax) | Multi-process master with preforking | **High-density Rust threads with low memory footprint** |
| **Kubernetes Health Probes** | Requires custom Django views or curl exec | Custom stats server / external scripts | **Built-in `/startup`, `/alive`, `/ready` out of the box** |
| **Traffic Shedding Under Load** | Requests queue in OS socket until timeout | Listen queue overflow / dropped packets | **Shared memory queue tracking; `/ready` returns 400** |
| **Database Migration Sync** | Requires manual `initContainers` or Helm hooks | Requires custom bash entrypoint wrapper | **Built-in `--check-migrations-apply` before `/startup`** |
| **Edge Bot & Scanner Shield** | Hits Django view layer; requires Nginx sidecar | Requires complex regex rewrite rules | **Built-in Fast-404 (<50µs drop, zero log spam)** |
| **DoS & Flood Rate Limiting** | Requires Redis middleware or external WAF | uWSGI internal cache limiter | **Built-in Token-Bucket Rate Limiter with proxy headers** |
| **Prometheus Metrics** | Requires `django-prometheus` polluting URLs | Requires `uwsgi-exporter` sidecar container | **Built-in `/metrics` endpoint with shared memory metrics** |

## Why Gunicorn Creates Friction in Kubernetes

### 1. Memory Multiplication vs. Cost-Effective Concurrency
Gunicorn's traditional multi-process model forks `2 * CPUs + 1` independent OS processes:
- **Duplicated Memory Tax:** Every forked Gunicorn process duplicates Python's runtime, Django models, templates, and imports in RAM. To achieve high concurrency, teams must either pay for expensive, oversized cloud nodes or risk container OOM kills (`SIGKILL`, exit code 137) when memory limits are reached.
- **The Hurricane Advantage:** Hurricane executes on a unified Rust core (powered by [Granian](https://github.com/emmett-framework/granian)) with native thread-level parallelism (`blocking_threads` and `runtime_threads`). You achieve high multi-worker concurrency and maximum request density inside each Pod without the heavy RAM multiplication of forked Python processes, dramatically reducing cloud compute costs while maintaining predictable memory limits.

---

### 2. Lack of Native Kubernetes Probe Coordination
In Kubernetes, health checks cannot merely verify if a web server process is alive:
- **Startup Latency:** Heavy Django applications require time to load models, compile templates, and initialize caches. With Gunicorn, developers often rely on simple HTTP ping views; if the database is temporarily slow, the liveness probe kills the container before it finishes booting.
- **Congestion Visibility:** When Gunicorn's worker threads are all blocked on slow queries, additional requests pile up in the OS socket backlog. Kubelet continues routing ingress traffic to the overwhelmed pod because the `/ping` view might still squeak through or fail unpredictably.
- **The Hurricane Solution:** Hurricane implements all three native Kubernetes probes:
  1. `/startup`: Only reports `200 OK` once preflight database migrations and cache checks succeed.
  2. `/alive`: Liveness probe that detects deadlocked worker threads and triggers automated container restarts.
  3. `/ready`: Monitors queue backlog in POSIX shared memory. If the worker queue is congested, it immediately returns `400 Bad Request`, signaling `kube-proxy` to shed ingress traffic to sibling pods without killing the container.

---

### 3. Eliminating the Ingress / Nginx Sidecar Requirement
Traditional Django Gunicorn deployments often require injecting an **Nginx sidecar container** inside the Pod to handle:
- Static and media file serving.
- Blocking bot scanners (`.php`, `/.env`, `/wp-admin/`).
- Enforcing rate limits to prevent denial-of-service.

**The Hurricane Solution:**
Hurricane embeds these capabilities directly into its gateway:
- **Fast-404 Security Shield:** Intercepts dictionary attacks at the socket layer in microseconds, protecting Django middleware and database connection pools from being exhausted by botnets.
- **Token-Bucket Rate Limiter:** Operates silently in-memory with automatic `X-Forwarded-For` and `CF-Connecting-IP` resolution.
- **Static & Media Asset Delivery:** Serves collected assets directly from disk without requiring an auxiliary Nginx container.

## Migration Blueprint: Switching from Gunicorn to Hurricane

Migrating an existing Kubernetes Deployment from Gunicorn to Hurricane requires zero changes to your Django views or routing.

### Step 1: Install Hurricane
Add `django-hurricane` to your project dependencies:
```bash
uv add django-hurricane
# or
pip install django-hurricane
```

In `settings.py`:
```python [settings.py]
INSTALLED_APPS = [
    # ...
    "hurricane",
]
```

### Step 2: Update Kubernetes Container Command

**Old (Gunicorn):**
```yaml
command:
- "gunicorn"
- "myproject.wsgi:application"
- "--bind=0.0.0.0:8000"
- "--workers=4"
- "--timeout=60"
```

**New (Hurricane):**
```yaml
command:
- "python"
- "manage.py"
- "serve"
- "--port=8000"
- "--probe-port=8001"
- "--check-migrations-apply"
- "--req-queue-len=15"
```

Configure your Kubernetes probes to target port `8001` with `/startup`, `/alive`, and `/ready`, and your cluster gains instant zero-config resilience!
